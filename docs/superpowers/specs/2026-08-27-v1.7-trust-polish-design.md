# Stats v1.7 "Trust & polish" — design

**Date:** 2026-08-27 · **Branch:** `master` (`18c2b92`, tag `v1.6.0`) → `feature/v1.7-trust-polish` · **Status:** approved by owner work order

## Goal

Make Stats safer to trust unattended, clearer when monitoring is unhealthy, visually
consistent across all themes, quieter at sign-in, and more transparent about updates.
This batch stays Windows-only and does not restructure `Stats.Core` for portability.

## Global constraints

- Preserve poller-thread ownership of LibreHardwareMonitor. UI work is dispatched; no
  new UI-thread hardware access is introduced.
- Preserve fan-control safety semantics. Fatal cleanup calls the existing
  `FanController.RestoreAll()` rather than creating another release path.
- Every new persisted setting has a default and old settings files continue to load.
- `MetricGroup` is unchanged.
- `H.NotifyIcon.Wpf` remains pinned at 2.3.2. No UI or toast package is added.
- All control-template palette references use `DynamicResource` so brush replacement
  by `ThemeManager` continues to update live.
- The Store PowerShell shell cannot verify elevation, ETW, hardware, or visual
  behavior. Build and tests are the automated gate; the PR carries an owner checklist.
- The release is not tagged from this branch.

## 1. Crash safety and diagnostics

### Persistent trace log

`App.OnStartup` installs the file listener before other startup work. Logs are written
to `%AppData%\Stats\logs\stats-YYYYMMDD.log`, with `Trace.AutoFlush` enabled. Startup
prunes older `stats-*.log` files so only the newest seven remain. Listener setup is
best-effort: a logging failure must not prevent sensor or fan initialization.

The Settings tab gains a **Diagnostics** section with **Open log folder**. The folder
is created if necessary and opened with the Windows shell. A failure is surfaced
inline rather than silently ignored.

### Fatal exception handling

`App` registers:

- `DispatcherUnhandledException`
- `AppDomain.CurrentDomain.UnhandledException`
- `TaskScheduler.UnobservedTaskException`

Fatal handlers are guarded with `Interlocked` so cleanup runs once even if exception
surfaces race. They trace the exception, best-effort call
`FanController.RestoreAll()`, and flush all trace listeners. They do not mark a
dispatcher exception handled and do not otherwise convert fatal failure into
continued execution. `UnobservedTaskException` is logged and flushed only; it is not
treated as a fatal fan-cleanup path and is not marked observed.

Normal `OnExit` ordering remains:
`SensorPoller.Stop()` → `FanController.RestoreAll()` → reader disposal only after a
successful join → final settings save.

## 2. Runtime sensor-failure visibility

`SensorPoller` tracks a failure episode:

- consecutive failed reads,
- the local time of the first failed read,
- the latest error text,
- and the failing backend names when supplied by a composite reader.

The count resets on the next successful read. A health-change event exposes immutable
episode state to the composition root without moving sensor reads off the poller
thread.

`CompositeSensorReader` continues returning the healthy children's values each tick.
When one child fails, it reports that child's `Name` and first-line error for the
current read. `SensorPoller` includes those partial failures in health state even when
the composite read itself returns a snapshot. A fully failed top-level read uses the
reader name plus the thrown exception.

After three consecutive unhealthy reads, the dashboard shows:

`Sensor reads failing since HH:mm — <backend>: <first line of error>`

Multiple failing backends are joined compactly. The banner clears automatically on
the first wholly healthy read. Startup-only degraded status remains separate and is
not cleared by transient runtime recovery.

Tests cover counting, first-failure time stability, composite backend attribution,
the threshold transition, and reset/recovery.

Create `Views/Controls.xaml` and merge it from `App.xaml` immediately after
`Theme.xaml`. It owns implicit styles and hand-written templates for:

- slim `ScrollBar`,
- `Slider`,
- `ProgressBar`,
- `ComboBox` and its popup,

- `ContextMenu`, `MenuItem`, and submenu popups,

Existing Button and TextBox styles remain in `App.xaml`. Every new palette reference

Rendering is owner-verified for every window under all five presets.

## 4. Startup behavior

### Minimized launch

`--minimized` is parsed case-insensitively. Startup still constructs the dashboard,
tray icon, services, and poller, but skips the initial dashboard `Show()`. The first
tray click uses the existing `ShowDashboard()` path and performs an immediate refresh.

The installer's logon Scheduled Task launches:

`"<installed Stats.App.exe>" --minimized`

### In-app autostart

The Settings tab gains a **Startup** section with **Start Stats when I sign in**.
This is live OS state, not a persisted `AppSettings` boolean. On settings load/open,
Stats queries task `Stats` with `schtasks /Query`. Toggling on creates the same task
as the installer (`ONLOGON`, `HIGHEST`, interactive token, current executable, and
`--minimized`); toggling off deletes it.

Task operations are asynchronous from the UI perspective. Their nonzero exit codes
and stderr are shown inline, and the checkbox is refreshed from the actual task state
after each operation. Command construction is centralized so installer and app
parameters can be compared during review.

## 5. About and update polish

The Settings tab gains an **About** section:

- entry-assembly product version,
- **Check for updates**,
- inline status.

Versions whose first three components are `0.0.0` display a development-build message
and do not contact GitHub. Manual checks reuse `UpdateService.CheckAsync`. A newer
release feeds the existing dashboard update banner; no update displays **Up to date**;
failures display an explicit manual-check error while automatic checks remain quiet.

The dashboard update banner adds a **What's new** hyperlink bound to
`UpdateInfo.ReleasePageUrl` and opened with the shell.

The Hardware settings section adds **Restart now** beside the existing restart
status. It starts the current executable, then calls the existing `ExitApp()` so the
poller stops, fans restore, bounds save, and settings flush through the normal path.

## 6. Update integrity

GitHub Actions computes SHA-256 for the built installer and supplies a release body
containing a machine-readable:

`SHA256: <64 lowercase hexadecimal characters>`

`UpdateChecker` parses this optional line from the release body into
`UpdateInfo.Sha256`. Old releases without the line remain eligible.

`UpdateService.DownloadAsync` always retains the existing HTTPS and size checks. If a
hash is present, it hashes the completed file and compares case-insensitively. A size
or hash mismatch deletes the downloaded file and throws, allowing the existing update
error UI to offer retry. Cancellation also leaves no successful-looking installer.

Tests cover hash parsing, absent and malformed lines, successful verification, and
mismatch deletion.

## 7. Correctness and responsiveness

- Add `Delay=250` to the poll-interval and overlay-font-scale slider bindings, matching
  the fan slider. Overlay opacity is unchanged because it was not part of the approved
  scope.
- `MetricTileViewModel.HistoryWindowTag` is calculated from actual
  `MetricHistory.Capacity × PollIntervalSeconds`. Formatting uses the effective
  duration, so a capacity-clamped 60-minute request at 0.5 seconds reads `30m`.
- Dashboard, Peaks, and Fans bounds mutations share a dispatcher debounce of about
  five seconds before `SaveSettings()`. Existing exit-time saves remain the final
  backstop.
- Add root `Directory.Build.props` with `TreatWarningsAsErrors=true`.
